# 0010 ジョブの Request ID は例外の記録の後に戻す

- 状態: 採用

## 背景

ジョブの中では Request ID をジョブ用の物に入れ替える。失敗したときに、失敗のイベントで ID を元に戻すと、Laravel が後で例外を記録するときのログの `request_id` は元の ID になり、知らせの Request ID（ジョブの ID）と食い違う。知らせの ID でログを引けない。

## 選んだ物

Laravel が例外を記録した後に戻す。

| 動き方 | 戻す所 | 理由 |
| --- | --- | --- |
| ワーカー | 次の周の頭（`Looping`）か `WorkerStopping` | `Worker::runJob()` は `process()` の後で `report()` を呼ぶ。`JobAttempted` はそれより前に出る |
| sync（出した側に ID がある） | `JobAttempted`（呼び出し側へ戻る所） | `report()` は呼び出し側（HTTP など）で呼ばれ、いつになるか分からない。呼び出し側の Context を戻しておく |
| sync（出した側に ID が無い） | 入口の終わり（`CommandFinished`・`RequestHandled`・アプリの terminating）、次のジョブ、`settle()` | 呼び出し側の例外の記録もジョブの ID で書かれるよう残す。入口の後まで残さない |
| 成功 | `JobProcessed` | 記録する例外が無い |

sync で失敗して呼び出し側（HTTP など）で記録されたときは、失敗のイベントで結び付けた入口でジョブの行を出す。例外の記録は呼び出し側の ID で書かれるので、知らせの Request ID は次のように分ける。

```text
Request ID: {ジョブの ID}（ジョブの中のログ）
発端の Request ID: {呼び出し側の ID}（例外の記録はこの番号）
```

呼び出し側に ID が無ければ、JobAttempted で戻さずジョブの ID を Context に残し、入口の終わりで戻す。呼び出し側の例外の記録もジョブの ID になり、知らせと揃う。部品が残した ID は覚えておき、後のジョブの payload に写っても「発端の Request ID」には使わない（2 つ目の sync のジョブの知らせに、1 つ目のジョブの ID が発端として出ないように）。

詳しい流れは [design.md](../design.md#ジョブの入口と-request-id)。

## 選ばなかった物

| 案 | 選ばなかった理由 |
| --- | --- |
| 失敗のイベントで戻す | ログと知らせの Request ID が食い違う |
| sync も Looping で戻す | sync には周が無く、HTTP の残りの処理がジョブの ID のまま書かれる |

## 代償

- ワーカーでは、失敗した後から次の周の頭までの間に書かれたログもジョブの ID になる
- sync で失敗して呼び出し側で記録されたときは、ジョブの中のログと例外の記録が別の番号になる。知らせに両方を書いて補う
- 呼び出し側に ID が無い sync の失敗では、入口の終わりまで、呼び出し側の残りのログもジョブの ID になる
