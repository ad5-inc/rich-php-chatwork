# 0011 値の書き出しの形を含む文言は省く

- 状態: 採用

## 背景

形の分からない例外の文言は、規則で伏せて送っていた。コードのレビューを 4 回回して、4 回とも値の書き出し（print_r・var_export・serialize・入れ子の JSON など）の中の秘密が漏れる指摘が最も重いものとして出た。

- オブジェクトの書き出しの protected・private の値
- serialize の長さで区切られた値（長さがずれると規則が外れる）
- 入れ子・閉じ括弧の数え方の抜け

正規表現でこれらを追い続けても「これで全部」とは言えない。

## 選んだ物

形の分からない例外の文言と notice の地の文の行は、**値の書き出しの形を含むなら、伏せずに丸ごと省く**。

- 判定は、文字を直し全角を揃えた後、伏せる前に行う
- 目印は `Redactor::DUMP_MARKERS` の 1 か所: 改行（複数行）、`=>`、serialize（`s:N:"`・`a:N:{`・`O:N:"`）、`Array (`・`… Object (`・`array (`・`::__set_state`、JSON（`{"`・`["`・`\"`）、`%5B`・`%5D`
- 当たったら、メッセージの枠を「（値の書き出しを含むので省いた。ログを見る）」にする。件名・種類の行・Request ID は今のまま出るので、種類とログを引く鍵は残る
- notice は行ごとに省く。notice の枠・前後のコード・組み立て直す文言（DB・HTTP クライアント）には当てない
- 1 行の普通の文には、今までの伏せる規則をそのまま当てる

## 選ばなかった物

| 案 | 選ばなかった理由 |
| --- | --- |
| 書き出しの形ごとに規則を足し続ける | 形が尽きず、抜けが秘密の漏れになる（4 回続けて同じ種類の指摘が出た） |
| 書き出しを解析して値だけ伏せる | 文言は途中で切れていることもあり、解析が失敗したときの扱いが同じ問題に戻る |
| 文言を全部送らない | 1 行の普通の文で種類が分かる利点を捨てることになる |

## 代償

- 普通の文でも目印に当たれば省く（`=>` を含む文・複数行の文・`{"` を含む文など）。秘密を出さない方を上に置いた（[0006](0006-goals-in-order.md) のゴール 2 がゴール 4 より上）
- 省いた文言はログで見る
- notice の枠（`code`）は使う側が中身を決める物として、伏せる規則だけを当てる。値の書き出しを枠に入れるなら、使う側で中身を確かめる
