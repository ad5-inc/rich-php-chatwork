# 0008 届けるための仕組み

- 状態: 採用

## 背景

ゴール 1（黙殺しない）のため、部品自身が失敗しても「知らせ」か「ログの送れなかった記録」のどちらかが必ず残るようにしたい。Chatwork の API には件数の上限があり、まとめて送ると全部が消えることもある。

## 選んだ物

| 場面 | 動き |
| --- | --- |
| 本文を組み立てられない | 値を含まない最小の知らせを送る。間引きのキーも作れなければ、主に見る例外を辿らず「外側の例外のクラス＋投げた場所」で作る |
| 送れない | 間引きの印を消し、数えた回数を戻す。次に同じ例外が起きたらすぐ送り直す |
| 部品の失敗 | ログに部品の例外を生で書き（文言と呼び出しの並び）、元の例外のクラスと Request ID を添える |
| 全体の上限 | 1 分に `max_per_minute` 件（既定 20）。超えた分は短いクラス名ごとに数え、次の知らせに多い順 3 つを足す |
| 送る環境で送り先が空 | 最初の例外でログに警告を 1 度だけ書く |

例外の知らせにも notice にも当てる。表の細かい動きは [design.md](../design.md#失敗したときの動きゴール-1)。

## 選ばなかった物

| 案 | 選ばなかった理由 |
| --- | --- |
| 失敗したら何も送らない | 知らせが黙って消える |
| 失敗したら元の文言をそのまま送る | 秘密が出る（ゴール 2 を破る） |
| 全体の上限を置かない | 障害のときに API の上限を超え、まとめて消える |

## 代償

- 最小の知らせは種類が分かりにくい（中身はログで見る）
- 上限で送らなかった件数と、間引いた回数は「おおよそ」。障害が止まると最後のまとまりの件数は届かない
- 元の例外の記録はどれもログにあるので、それで補う
