# 0012 例外の文言は必ず出し、設定は送り先だけにする

- 状態: 採用（0005・0011 を置き換える）

## 背景

0.4 では、形の分からない例外の文言は `send_message` を true にしたときだけ送り、値の書き出しを含む文言は丸ごと省いていた。使う側で試すと、`report(new RuntimeException('…'))` の知らせに文言が出ず、件名の「RuntimeException」だけでは何のエラーか分からなかった。

例外に入れる文字列は、開発者が何が起きたかを書くための物で、秘密を入れる場所ではない。文言を隠すことは秘密を守ることと重ならない。秘密が混ざるときは、その値を伏せれば足りる。

あわせて、設定が 16 個あり、使う側（3 つのアプリ）は想定も管理もしていなかった。並べると違いはあったが、アプリごとに分けたい理由のある違いは無かった。既定の値が悪い所（間引きの置き場が database）は、どのアプリも同じ設定を書いて直していた。

## 選んだ物

- ゴールの 2 に「知らせだけで何のエラーか分かる。例外に入れた文字列は必ず出す」を置き、秘密・個人情報（3・4）より上にする
- 形の分からない例外の文言は、どんな文言でも省かずに出す。秘密と形の分かる個人情報は、文言の中でその値だけを伏せる
  - 値の書き出し・複数行も全部出す。serialize の protected・private のプロパティと長さを偽った値は伏せる。`pin` を秘密のキーに足した
  - 写したプロセスの文言は、引用符の中のコマンドラインだけを伏せる
- notice の行も同じく省かない
- 設定は送り先の 2 つ（`.env`）だけにする。ほかは部品で決める（件名の頭は `{app}（{env}）`、testing・local では送らずに本文をログへ、待つのは 180 秒、間引きの置き場は file、そのほかは 0.4 の既定）

## 選ばなかった物

| 案 | 選ばなかった理由 |
| --- | --- |
| `send_message` の既定を true にして設定は残す | 使う側は設定を想定していない。残すと、書き方しだいでまた文言が消える |
| 値の書き出しを含む文言は 1 行目だけ出す | 例外に入れた文字列の一部が欠ける |
| 書き出しの中の値を全部伏せる | キーが分からなくなり、何が起きたかが読めない。秘密のキーの値は伏せるので足りる |

## 代償

- 普通の語のキー（`name` など）の値・キーの無い値・氏名のような形の無い個人情報は、伏せずに部屋に出る。送り先の部屋には文言を見てよい人だけを入れる
- アプリごとに件名・待つ秒数などを変えられない。変える理由が出たら、その時に設定を足す
- 部品の中では設定のキーを読み続けている（テストで値を変えるため）。README には書かず、使う側の設定としては扱わない
